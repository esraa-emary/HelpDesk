Deliverable 2

Context & access plan

Access is granted per task, not per tool. The default is the smallest context that lets the AI do the job — never the whole repository "just in case."

Tier 1

Prompt-only

No files attached. Used for naming conventions, drafting a plan in words, explaining an error message the human pastes in, or brainstorming test case ideas.

e.g. "What edge cases should a ticket status transition guard cover?"
Tier 2

Single file / single module

One component, one endpoint file, or one test file is shared. Used for well-scoped UI components, isolated bug fixes, and writing tests for a function whose contract is known.

e.g. TicketForm.jsx only — not the whole /components folder.
Tier 3

Multi-file / repo context

Granted only when the task genuinely spans layers (e.g. a status change that must update the API, the store, and the dashboard query). Always paired with a required human review step and a diff walkthrough before merge.

e.g. status workflow: model + API handler + dashboard query.
Restricted

Never auto-granted

Auth/permission code, production credentials, real user ticket data, and anything touching the assignment-logic decision that Day 1 left open. These require an explicit, task-specific exception approved by a human reviewer — not default tool access.

Deliverable 3

AI coding workflow — HD-102

One real task from the Day 2 board, walked through the full controlled loop: frame → plan → review plan → implement → inspect → verify → decide.

HD-102

Prevent invalid ticket status transitions

Sprint 1 status model is Open → In Progress → Resolved → Closed. A ticket must not be able to jump from Open directly to Closed, or move backward from Closed to Open without an explicit reopen action.

  1. 01

    Frame the task

    Written before opening any AI tool: "Add a guard function that validates a proposed status transition against the approved Sprint 1 state model, and rejects/reports invalid transitions. No change to the state model itself — that's already decided."

  2. 02

    Prompt (Tier 2 access — single file)

    "Here is ticket.service.js and the four approved statuses (Open, In Progress, Resolved, Closed). Propose a plan for a transition-guard function before writing code. Don't touch unrelated functions in this file."

  3. 03

    AI plan before coding

    AI returns a short plan: a transition map object, a pure isValidTransition() function, an explicit "reopen" action separate from the forward flow, and unit test cases for every legal and illegal pair.

  4. 04

    Human review of the plan

    Reviewer checks the plan — not code yet — against the Day 1/2 state model. Confirms the reopen action is separate (matches the "Closed → Open needs an explicit action" rule) and that no new status is being introduced. Plan approved with one change: log rejected transitions for later audit.

  5. 05

    Implementation

    AI implements the approved plan only. Human keeps the diff small on purpose — one function, one map, one test file — so the review in the next step stays honest.

  6. 06

    Output inspection

    Full diff read line by line. Checked for: scope creep (did it touch anything outside ticket.service.js?), hidden assumptions (does it silently allow an untested transition?), and whether the log statement matches the team's existing logging pattern.

  7. 07

    Verify → decide

    Unit tests run for all 12 status pairs (4×4 minus identity). Manual run through the UI: attempted Open → Closed in the browser and confirmed rejection. Decision: keep, pending standard PR review before merge to Done column.

Deliverable 4

Debugging & verification example

Investigation always comes before a patch request. Evidence decides the outcome, not how confident the explanation sounds.

HD-108 PARTIAL

Bug: resolved tickets reappear in the Open queue

Reported by support staff: a ticket marked Resolved shows back up in the manager's "Open" list a few minutes after being reassigned to a different agent.

1 — Reproduce

Confirmed locally: resolving a ticket, then reassigning it, flips its status field back to "Open" in the database.

2 — Read the diff / blame

Git blame on the assignment handler shows a recent AI-assisted change to reassignTicket() that resets a "status" field for an unrelated reason (queue position), overwriting the real status field with the same name.

3 — Check logs

Server logs show two writes to the same ticket row within 40ms — the resolve write, then the reassignment write — confirming a race/overwrite, not a UI caching issue.

4 — Ask the AI to explain, not fix

AI is given only the two functions involved and asked to explain the field collision — not to produce a patch yet. Its explanation matches the log evidence: a naming collision between "status" (ticket state) and "status" (queue position) in the same update payload.

Decision

Revise. The original AI-assisted change is not rolled back entirely — the reassignment logic itself is correct — but the field name collision is renamed (queuePosition instead of reusing status), re-reviewed with the same plan-first process, and covered with a regression test that resolves then reassigns a ticket in sequence.

Deliverable 5

Staying current plan

AI tool behavior changes fast. The team refreshes assumptions on a schedule instead of relying on memory of how a tool used to work.

Before each new sprint

Whoever owns the AI-assisted tasks that sprint checks the tool's official changelog or documentation for anything that changed since last sprint — new model version, new default permissions, deprecated features.

Trusted sources to check

  • docs.claude.com — official product & API documentation
  • support.claude.com — feature and usage updates
  • anthropic.com/news — model and policy announcements

Standing rule

No engineer assumes a tool's context limits, access defaults, or capabilities from memory alone when starting a new type of task with it. If it's the first time using a given AI capability for HelpDesk Lite, the source is checked first.
