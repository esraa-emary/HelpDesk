01 · Requirement Framing

What this version is actually trying to deliver

Core problem

Employees report issues through email, chat, and informal follow‑up with no shared record. Requests get duplicated, ownership goes unclear the moment a thread goes quiet, and staff spend more time re‑asking "who has this?" than resolving anything.

Intended outcome

Every request enters one workspace, gets a visible state and a visible owner, and can be tracked from submission to resolution without a side conversation. Managers can see what's open, stuck, or done without asking.

In scope — v1

  • Single structured intake form
  • One shared ticket queue
  • Manual / rule‑light assignment
  • A small, explicit status set
  • Basic manager visibility view
  • Simple category & priority tagging

Non‑goals — v1

  • SLA timers & escalation automation
  • Full self‑service knowledge base
  • Auto‑ingest from email / chat
  • Custom workflow builder
  • Advanced analytics / reporting
  • Multi‑team routing logic

Unresolved questions

These are open by design — planning past them now would mean planning on guesses.

  1. What fields are required at submission — and which are optional?
  2. Who assigns ownership: self‑pick, auto‑assign, or manager‑assign?
  3. What is the full state machine — how many states, and what moves a ticket between them?
  4. What exactly does a manager need to see on day one?
  5. Where is the line between v1 and v2 — especially for self‑service content?
  6. Are category and priority set by the requester, or set at triage?

Major risks

Scope

Drifting from "lightweight internal tool" toward a full enterprise platform before v1 ships.

Adoption

A workflow too rigid for how support actually happens gets abandoned back into email.

Ownership

An undefined assignment model reproduces the exact "who has this?" problem being solved.

Sequencing

Building visibility or automation features before the core state machine is agreed.

02 · Planning‑Ready Breakdown

Work areas, and what they're waiting on

Eight work areas fall out of the requirement. Each is tagged by whether it can move forward now, or is blocked on one of the six open questions above. Expand a row for the first layer of breakdown.

WA‑A Request Intake Ready
  • Draft the minimum required field set (title, description, category)
  • Decide optional vs required fields — depends on Q1
  • Build the submission form UI
WA‑B Ticket Data Model & State Machine Ready to draft
  • Define ticket entity: id, requester, owner, state, category, priority, timestamps
  • Propose a minimal state set for review — feeds Q3
  • Define allowed state transitions
WA‑C Ownership & Assignment Blocked
  • Choose assignment model — blocked on Q2
  • Define reassignment / hand‑off behavior
  • Notify owner on assignment
WA‑D Queue & Ticket Views Ready
  • List view: all tickets, filterable by state and category
  • Detail view: single ticket, full history
  • Depends on WA‑B data model being drafted first
WA‑E Manager Visibility Blocked
  • Confirm what managers need on day one — blocked on Q4
  • Workload‑by‑owner view
  • Open / stuck / done counts
WA‑F Self‑Service / Knowledge Base Deferred
  • Out of v1 unless Q5 resolves otherwise
  • Candidate for v2 once repeat‑question patterns are visible in real data
WA‑G Notifications & Follow‑up Blocked
  • Depends on WA‑C assignment model being settled first
  • Define minimum notification set (assigned, status change)
WA‑H Access & Permissions Ready
  • Three roles: requester, support staff, manager
  • Define what each role can view / edit

Sequence & dependency logic

  1. First: run the clarification pass on the six open questions — at minimum, the state machine (Q3) and ownership model (Q2), since almost everything else reads from those.
  2. Then: draft the ticket data model and intake fields in parallel — both only need the clarification pass, not each other.
  3. Then: build the queue and ticket detail views on top of the agreed data model.
  4. Only once ownership is settled: build assignment and notifications.
  5. Last, and only if scope allows: manager visibility (needs real ticket data flowing) and — separately — revisit self‑service as a v2 candidate, not a v1 task.

04 · Walkthrough

Recording script — 2 minutes

This page is the leave‑behind; the recording is the reasoning behind it. Use this timing as a guide when recording the walkthrough video deliverable.

0:00–0:25

The problem

Support requests come in through email, chat, and informal follow‑up. Nothing is shared, so ownership disappears the moment a thread goes quiet — that's the actual problem, not "we don't have ticketing software."

0:25–0:55

What matters most

One shared queue, a visible owner per request, and a small honest set of states — before anything about automation, self‑service, or reporting. Everything else in v1 supports those three things.

0:55–1:25

What's still unclear

Walk through the six open questions — required fields, the assignment model, the exact state machine, what managers need first, the v1/v2 line, and who sets category/priority. Name them as decisions to make, not gaps in the plan.

1:25–2:00

How the plan de‑risks delivery

Point at the board: nothing that depends on an open question starts before that question is answered. The team can begin on the data model and intake form today without guessing at ownership or manager reporting.
